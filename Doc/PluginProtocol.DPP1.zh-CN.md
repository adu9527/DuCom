# DuCom 插件协议 DPP/1

状态：收敛草案 v0.5，尚未发布或冻结。

日期：2026-09-08。语言：[中文](PluginProtocol.DPP1.zh-CN.md) | [English](PluginProtocol.DPP1.en-US.md)。本版变更：新增 `files.pickWrite` 目录模式、`files.createWriteTarget`、`files.hostPaths`、`ui.notify` 与滑轨 UI 节点（均为可选能力，见 §10、§11、§13）。

依据：多轮模型评审与用户决策收敛形成本文；评审过程稿已清理，以本文条款为准。

本文定义目标行为与开发者契约，不表示仓库已有插件运行时、沙箱或 SDK。示例是设计输入，不可当作现成 SDK 使用。中英文应同时更新；出现歧义时先以中文核对用户决策，修正两份文档，不依据翻译差异发布不兼容实现。

## 1. 目标与规范用语

MUST/必须表示合规要求；MUST NOT/禁止表示不可接受行为；SHOULD/应当表示偏离需说明理由；MAY/可以表示可选行为。文中的“拟议默认值”是待测试的宿主策略，不是永久冻结的线协议常量。

目标是保持核心职责和公开契约稳定，使已有能力范围内的新功能仅通过插件交付。新增宿主能力、安全修复和性能优化允许修改宿主实现，但不得无说明地破坏已发布插件。

核心职责包括串口收发、原始数据接收、显示、可靠日志落盘、基础设置和会话管理。插件是可移除的功能，不能成为这些职责的同步依赖。

首版必须满足：每插件独立进程、内置同构、故障强制终止、持久化禁用、一次故障一次提示、工具级资源预算、重启切换更新以及可验证的版本兼容。

## 2. 架构与安全边界

```text
DuCom Host
  Core: serial / receive / display / log writer
  Plugin supervisor: lifecycle / watchdog / resource policy
  Broker: validated IPC / permissions / bounded queues
  UI renderer: host-owned declarative controls
       | authenticated local IPC
       +-- Restricted Worker A: built-in background plugin
       +-- Restricted Worker B: built-in log-package plugin
       +-- Restricted Worker C: community plugin
```

每个插件激活实例 MUST 使用独立受管进程。插件代码、模块初始化、构造函数及依赖加载只能发生在该进程，不能先在宿主实例化再搬过去。宿主不加载插件 DLL，不依赖 ALC 卸载实现故障隔离。

宿主 MUST 管理进程树，禁止脱离监管的子进程和重复实例。普通插件默认不得创建子进程。工作进程与宿主不得运行在提升权限上下文；需要提升权限的宿主功能不能继承给插件。

进程隔离提供故障边界，不自动提供恶意代码沙箱。Windows 受限令牌/AppContainer 等访问限制与 Job Object 等资源/生命周期机制必须分别设计；Job Object 本身不是文件、网络或进程访问沙箱。

插件默认不能直接访问串口设备、宿主进程、宿主设置/日志目录或网络；所需资源通过宿主代理服务授予。运行时 MUST 阻止这些直接访问，而不能只在文档中禁止。若目标机器无法建立所需限制，宿主必须拒绝执行插件并说明原因，不得静默退回无限制进程。

具体 Windows 策略尚待实现验证，属于 §18 发布门禁。不承诺抵御操作系统漏洞、内核故障或所有恶意代码；不得把本草案宣传为已经验证的沙箱。

当前不要求官方签名、在线审批平台或插件市场。维护者自行审核并控制主分支合并；这只是源码治理，不能替代本机安装确认、包校验及运行时隔离。未审核包首次启用必须显示来源未知及其申请权限。不得根据目录名或 `com.ducom.*` 前缀认定包安全。

## 3. 包、身份与清单

目录是安装形态，`.dcpack` 是 ZIP 分发形态。包至少包含清单、入口 DLL 及其运行依赖；可以包含静态资源和本地化表。

```text
<plugin-id>/<version>/
  plugin.manifest.json
  Example.Plugin.dll
  [private dependencies and runtime metadata]
  assets/
  i18n/en-US.json
  i18n/zh-CN.json
```

| 字段 | 要求 | 语义 |
|---|---|---|
| `manifestVersion` | 必填，整数 | 清单格式版本，首版为 1。 |
| `id` | 必填，字符串 | 稳定插件 id，匹配 `^[a-z][a-z0-9-]*(\.[a-z][a-z0-9-]*)+$`。 |
| `name` | 必填，字符串 | 可读默认名称，不以缺失翻译键代替默认文本。 |
| `version` | 必填，SemVer | 插件版本。 |
| `protocolVersion` | 必填，`major.minor` | 最低所需 DPP 版本，不是编译 SDK 的版本。 |
| `minHostVersion` | 必填，SemVer | 最低宿主版本，协议满足也必须检查此项。 |
| `entryAssembly` | 必填，字符串 | 包根目录下的 DLL 文件名，不能包含路径分隔符。 |
| `entryType` | 必填，字符串 | 工作进程内部的入口类型；类型及构造约定随 SDK 冻结。 |
| `runtime` | 必填，对象 | `framework`、`rid`，示例 `net10.0`、`win-x64`；宿主必须实际支持该组合。 |
| `capabilities` | 必填，字符串数组 | 所需能力；首版均为必需项，未知或未实现项拒绝。 |
| `permissions` | 可选，字符串数组 | 请求的代理资源权限，默认空；未知项拒绝。 |
| `defaultCulture` | 可选，字符串 | 有本地化资源时必填，使用明确 culture 名。 |
| `description`, `author`, `homepage` | 可选，字符串 | 展示元信息，不作为身份认证依据。 |

清单是元信息唯一来源。宿主在任何插件代码执行前校验 UTF-8 JSON、字段类型、长度、版本、能力、权限、路径、包大小与身份冲突。重复 JSON 属性应拒绝；未知非必需元信息字段可以忽略，不得推导新权限。插件声明不能自授权限。

同一 id 同时只能选择一个安装版本；新包必须走显式更新流程。发现来源歧义或重复安装记录必须提示处理，不依赖目录枚举顺序。`com.ducom.*` 保留给官方，第三方不能注册该命名空间，但前缀不提供认证。

安装器必须拒绝路径穿越、绝对路径、ADS、链接/重解析点越界、大小写碰撞和解压膨胀；限制文件数、单文件/总解压大小及清单大小。安装目录在校验与加载之间不得被插件修改。包摘要用于标识内容和发现替换，不等于证明发布者可信。

## 4. 协议、SDK 与兼容

DPP 的长期契约是消息和行为，不是宿主内部 .NET 对象。C# SDK 是工作进程侧的适配层，不得引用 `DuCom`、`DuCom.Core` 或把它们的类型发布为契约。宿主和插件不共享 Dispatcher、Control、Stream、SerialPort、委托或进程内对象引用。

插件所需版本为 P，宿主支持版本为 H：

| 条件 | 行为 |
|---|---|
| 同 major，P.minor ≤ H.minor，且所需能力均可用 | 可进入后续校验；不保证依赖加载一定成功。 |
| 同 major，P.minor > H.minor | 拒绝并提示升级宿主。 |
| major 不同 | 明确拒绝，除非宿主另有明确实现和测试的旧 major 适配器。 |
| 宿主低于 minHostVersion，或 runtime/RID 不支持 | 拒绝并给出具体原因。 |

minor 只能加入可选能力/消息，不改变已发布字段含义。未知可选响应字段忽略；未知必需操作返回 `UnsupportedOperation`；不认识的错误码按通用失败处理并保留原码。未知枚举值必须安全拒绝或降级，规则随该 DTO 定义。

不得给已发布的插件实现接口增加必实现成员。消息字段新增必须有缺省语义；移除、更名、改变单位或收紧合法值范围需要兼容分析。主版本破坏性升级是最后手段，不能承诺永远不会发生。

SDK 包版本、协议版本、CLR AssemblyVersion 分开管理。固定 AssemblyVersion 可以是 SDK 工程策略，不是 IPC 兼容保证。工作进程中的共享 SDK 身份由 runner 统一；私有依赖不得覆盖 runner SDK。发布门禁必须运行旧 SDK 编译的真实插件，不得先重新编译再声称兼容。

## 5. IPC 与会话

首版拟采用 Windows 本地命名管道、异步双向消息和 JSON DTO。管道必须限制到预期本机主体，使用不可预测端点、一次性会话凭据并核对连接进程；不能只依赖插件自报 id 或可猜管道名。凭据不得写日志或放在公开命令行。连接失败必须受启动期限限制。

拟议帧格式：4 字节 little-endian 无符号 payload 长度，随后为 UTF-8 JSON；单帧默认上限 1 MiB，长度检查发生在分配 payload 前。单帧上限包括 base64 等编码膨胀；大数据必须分块，不允许无界读到结束。精确 schema、数值限制和测试向量须在 SDK 1.0 发布前冻结。

每条消息包含 `protocolVersion`、`sessionId`、`activationId`、`kind`、`operation`；请求/响应另含 `requestId`，响应携带 `result` 或结构化 `error`，二者互斥。事件携带订阅 id 与序号。标识符均为有界字符串，不能直接用作文件路径。

握手交换 runner 版本、包摘要、所需能力和宿主最终授权、限额；宿主以安装记录为身份依据。握手后只能使用该激活代次被授予的操作。陈旧、重复或跨代次消息不得产生副作用。

请求最多完成一次。响应丢失或进程退出不等于操作未执行；首版不自动重放有副作用的请求。输出提交使用调用方生成的稳定 `commitId`，宿主在激活代次内保留有界终态，可通过 `output.commitStatus` 区分 `preparing`、`committing`、`committed`、`aborted` 和 `unknown`；重复同一 `commitId` 只能返回既有终态，不能再次发布。取消是请求，强制终止才是无响应时的最后手段；取消之后的迟到结果不能重新提交任务。断连使普通会话令牌失效，但已记录提交终态仍可在宿主保留期内查询。

宿主必须限制连接、队列字节数、在途请求、订阅、速率和嵌套深度，在后台解析验证；UI 与串口热路径不得解析或等待插件消息。畸形帧、凭据错误、洪泛和重复严重违约导致连接关闭与故障停用。

## 6. 生命周期与故障恢复

```text
Discovered -> Validated -> Starting -> Activating -> Active
Active -> Stopping -> Disabled
Starting / Activating / Active / Stopping -> FaultDisabled
Validated -> Rejected
FaultDisabled -> Starting  [explicit user retry only]
```

`Rejected` 表示包不合规且未执行；`FaultDisabled` 表示一次启动/运行尝试失败并被持久化禁用。状态由宿主控制。每次启动分配新 `activationId` 和进程，旧实例未确认退出时禁止重试。

启动前先原子持久化尝试记录，再启动 worker；记录插件 id、版本、摘要、激活代次、宿主运行实例和阶段。记录失败则不自动执行插件。多宿主实例必须分别记账，不能覆盖对方档案。

激活中的 UI/订阅注册暂存，成功后一次发布；失败整体撤销。构造、加载或初始化失败与激活失败一样，只产生一次故障事件。

正常停用：立即关闭新调度并撤销业务代理权限及提交资格，摘除 UI，停止投递，丢弃排队工作，取消在途任务；在清理预算内请求 worker 停用，期限到后终止进程树并确认退出。清理期只允许受限的取消确认、清理应答和诊断，不允许继续业务访问或提交输出。故障或资源紧急情况可以跳过宽限直接终止。之后回收句柄及临时输出，拒绝迟到消息。

强制终止失败时保持 IPC 断开及禁用状态，提示“未确认退出”，不能谎报已结束，也不能阻塞主程序无限等待。宿主异常退出时，受管 worker 应由操作系统生命周期机制回收。

非预期崩溃、启动失败、无响应、调用超期、持续积压、资源违规或严重协议违例 MUST 停用插件。用户取消、输入错误、文件不存在等预期业务失败正常返回，不视为进程失控。错误分类必须是宿主控制的有限集合，不能允许插件把所有异常都伪装为预期失败。

## 7. 警告与重新启用

故障后 MUST 持久化禁用该插件 id，记录故障版本与摘要。应用重启、安装新版本、重新扫描目录均不能自动解除；只有用户明确操作可以重新尝试。版本变更可以提示有修复版本，不能代替用户同意。

每个失败的激活代次 MUST 弹出且只弹出一次故障警告。进程退出、IPC 断开、任务失败和清理异常要合并到同一故障记录；详细原因持续写诊断，不重复弹窗。用户再次启用并失败时，新代次必须再提示一次。若宿主已退出而无法显示，持久化待提示记录，在下次可用 UI 中显示一次恢复通知，不能因此自动启动插件。

警告使用非模态窗口，不夺走串口工作流的持续操作能力，内容包括插件名称/版本、原因、已停止或未确认退出状态、已禁用、建议排查修复后再启用，以及详情入口。不同插件同时故障可聚合展示，但不得遗漏故障条目。

提供在插件启动前生效的“禁用全部插件启动”入口，覆盖 BuiltIn。非正常退出后的档案只表示嫌疑，不能宣称精确归因；损坏档案采取保守恢复。不得自动删除插件包或用户数据。

## 8. 整个工具的资源预算

用户要求的“1 GB”适用于整个工具，不是单插件。本草案明确计量默认值为 **1 GB = 1,000,000,000 字节**；正式 UI 必须展示准确单位，不能混用 GB 与 GiB 或借单位转换提高预算。

主要预算指标为每个受管进程的 Windows private committed bytes 之和：宿主、全部 worker、受管辅助进程均纳入。它不是 GC 堆大小，也不等同于实际驻留物理内存；共享页不能通过简单相加 working set 可靠计量。另行观测系统可用内存和 working set，不能把两类指标混称为同一上限。

拟议默认预警值为总预算 80%，可配置但必须低于上限。达到预警值后暂停新插件激活/新增大任务，采集每进程占用、增长率、队列、在途任务和近期操作；限制或丢弃插件派生缓存和旁路工作。不得在主线程做 heap dump 或长时间 GC。

达到上限或预计即将耗尽保留量时进入紧急治理：优先终止已违反配额、持续异常增长或已无响应的插件。存在正常插件但无明确违规者时，可以按确定性资源策略停止高占用插件以保护核心，提示“总预算保护停用”，不能称其有 bug。多插件都异常时按证据逐个处理，不反复重启。

主程序必须保留经压力测试确定的核心预算与安全余量，将剩余预算分配给插件；单插件配额之和不能超过插件池，限制值由宿主握手告知。应使用 OS 级分配限制与进程监管，不仅依赖采样。CPU、进程数、IPC、磁盘输出及 UI 刷新也必须有限额，插件无权自行解除。

**本草案没有证明整工具瞬时内存绝不会超过 1 GB。** 宿主自身增长、内核缓冲和采样延迟均需验证；不得给包含核心的进程组设置“超限杀全部进程”来伪造保障。若所有插件停止后核心仍超限，报告宿主资源压力、限制非核心缓存/新任务并保留接收与日志优先级，不虚构插件责任。若合法核心负载本身无法满足预算，必须作为发布阻塞问题处理，调整实现或明确修订预算，不能静默宣称达标。

## 9. 期限与慢插件

| 操作 | 拟议默认策略 |
|---|---|
| 启动及握手 | 10 秒；超期停用。 |
| 激活 | 10 秒；超期回滚并停用。 |
| 普通短调用 | 2 秒；超期停用，不自动重试。 |
| 心跳 | 每 2 秒一次，连续 3 次缺失触发无响应判断。 |
| 长任务进度 | 5 秒内首次报告，此后最长 10 秒间隔；不能作为无限延期凭据。 |
| 正常停用 | 最多 3 秒，之后终止进程树。 |

日志打包等长任务必须先返回任务句柄，具有取消、进度、最大输入/输出和宿主批准的绝对期限。期限按任务类型与已知工作量制定，并在任务开始前告知；超过期限即使心跳仍在也算故障。进度不能证明有意义的进展，宿主还需检查处理字节、积压趋势及资源使用。

实时观察插件持续落后或不断丢数据时，宿主在有限窗口内评估；超过公布的积压/丢失阈值则停止该插件，不允许无限降质。单次瞬态丢块不直接等于插件故障。所有策略可随宿主优化，但必须受上限约束并向插件暴露实际值。

## 10. 能力、权限与宿主 API

能力表示可注册的扩展点，权限表示可访问的代理资源；二者独立校验。首版 manifest 中均按必需项处理，用户不批准必需权限则不激活；未来可选权限需要新 schema 或明确扩展，不暗中改变现有语义。

| 能力 | 首版行为 |
|---|---|
| `menu` | 宿主菜单描述与命令 id。 |
| `tool-page` | 宿主渲染工具页描述。 |
| `settings-panel` | 宿主渲染设置字段、校验和提交命令。 |
| `background-image` | 安全图片资产令牌、透明度及切换请求；不是任意覆盖层。 |

| 权限 | 代理资源 |
|---|---|
| `storage.own` | 插件私有配置和有配额的存储。 |
| `serial.read` | 接收数据旁路订阅与会话只读信息。 |
| `serial.logs.read` | 有边界的日志快照和分块读取；不要求 serial.read。 |
| `files.user-selected.read` | 通过用户选择取得的限定文件/目录读令牌。 |
| `files.user-selected.write` | 用户选定目标的事务式文件输出令牌。 |

首版不提供串口发送/控制、网络、ReceiveTransform、SendTransform、任意窗口嵌入或插件互调。保留名称不等于实现，使用未开放能力必须拒绝。

系统文件选择器由宿主发起，需用户手势或明确操作，限频且可取消；返回有范围、期限及操作限制的令牌，不返回可任意使用的宿主对象。拒绝授权返回 `PermissionDenied`，正常取消返回 `Cancelled`。句柄每次调用都检查权限和激活代次，停用立即失效。`files.pickWrite` 支持两种模式：保存文件（默认）与输出目录（`mode: "directory"`）；目录模式返回目录令牌，并由宿主把该目录记为本插件的已授权输出目录，供后续无对话框的写目标创建（§13）复用。

资源错误建议采用稳定码：`InvalidArgument`、`PermissionDenied`、`Cancelled`、`NotFound`、`ResourceLimit`、`DeadlineExceeded`、`UnsupportedOperation`、`SessionExpired`、`InternalError`。面向用户消息可本地化，开发者不能解析消息文字判断状态。

## 11. UI 贡献与本地化

宿主 MUST NOT 加载插件 UserControl、任意 XAML、脚本、绑定表达式、可执行转换器或插件 DLL。首版支持有界的文本字段、标签、按钮、复选框、下拉、滑轨、列表、进度、图片与布局描述；控件种类和 DTO schema 在 SDK 发布前冻结。滑轨节点（`slider`）以 `fieldId` 参与表单收集，携带最小值、最大值与步长，宿主负责渲染与取值回传。复杂独立插件窗口不属于首版范围。

所有 UI 更新在宿主验证后批量编组，限制节点数、层级、图片解码尺寸、列表长度、更新频率及单次工作量。声明式 UI 也可能触发昂贵布局或图片解码，不能因此免除预算。解码等高风险工作应在受限辅助进程完成并计入总预算。

贡献使用稳定 `contributionId`；同插件内唯一，跨插件身份为 `(pluginId, contributionId)`。默认排序为 `(order, pluginId, contributionId)`，order 默认 100；用户排序按稳定身份持久化。背景图首版独占，用户选择优先，否则按排序选取；胜者停用时选择下一个已激活且合格的贡献，不自动启用被禁用插件。

持有 `tool-page` 能力的插件可调用 `ui.notify(title, message, revealPath?)` 请求一次性结果提示：宿主以该插件的工具窗为属主显示模态对话框，`revealPath` 非空时在对话框关闭后于资源管理器中定位该文件。标题、消息与路径长度受限；展示失败返回 `InternalError`，不重试、不排队，更不能替代故障通知通道（§7）。

本地化文件为有界 UTF-8 字符串键值表，回退为 UI culture → 父 culture → 插件 defaultCulture → DTO/清单默认文本。翻译内容不执行代码，不自动加载外部 URL。缺失键记诊断，不以 `@key` 作为最终可读名称。

## 12. 串口旁路与日志快照

核心接收、发送与落盘 MUST NOT 等待插件。主日志记录原始既有语义，插件不能替换、过滤或延迟它。现有内部同步 tap 不可直接作为第三方调用入口。

接收旁路由宿主有界复制后投递，禁止把池化核心缓冲直接跨边界使用。每块包含会话实例 id、订阅 id、序号、字节偏移、长度及时间戳；时间基准、会话重开和计数重置语义必须随 DTO 固定。IPC 使用有界编码块，所有副本和队列计入资源预算。

默认队列满时丢弃最旧的未发送观察块以保持新鲜度，同时报告 gap 范围与累计丢失量；同订阅保留块有序，不承诺不同订阅之间总序。停用时丢弃该订阅剩余块，不能把缺口伪装为连续数据。持续落后按 §9 停用。

需要完整数据的插件使用日志快照补读。快照请求在宿主日志写队列的既定位置刷新并取得文件长度边界，不暂停串口；返回宿主管理的不可伪造令牌和文件段元信息。按快照长度分块读取，不能读到后续追加部分。

必须定义快照保留期、字节/句柄配额、日志轮转、删除及取消行为。无法读取时明确返回错误或“快照失效”，不能生成看似完整的截断文件。日志服务与实时接收服务分别授权，打包插件不需要额外申请 `serial.read`。

## 13. 存储与外部副作用

配置以插件 id 隔离，宿主执行原子写入和大小限制；schemaVersion 由插件定义，迁移失败保留原件。卸载默认不删除用户数据，删除需独立确认。插件不能自行打开宿主全局配置文件。

日志打包等输出写入由宿主管理的临时结果。当前 DPP/1 草案使用 `output.begin`、严格顺序的 `output.write(token, offset, base64Chunk)`、`output.commit(token, targetToken, commitId)`、`output.commitStatus(commitId)` 和 `output.discard`：begin 只返回不透明 token、总额度及块上限，**不得返回可写路径**；块必须从 offset 0 连续追加，重复、乱序、空块、超块或超额在写入前拒绝。宿主独占暂存和快照目录，worker 只通过授权分块读取/写入。提交分为 Preparing/Committing/Committed/Aborted 等阶段，耗时复制和 flush 不持有撤权锁，最终同卷 rename 是短提交线性化点，发布最多一次。输出、快照和目标侧 publication staging 同时受每插件累计限额及独立的宿主进程暂存磁盘共享额度约束，扩容或复制前原子预留，实际删除成功后归还；该宿主共享额度只覆盖单个宿主进程，不宣称是多宿主跨进程磁盘总额，也不属于整个工具的 1,000,000,000 字节内存预算。成功校验后才将宿主暂存发布至授权目标；跨卷先有界复制到目标卷内的宿主登记临时文件，保持打开的宿主句柄并从该句柄执行最终 rename，不能在关闭后重新按路径发布。覆盖授权绑定用户选择的路径，不绑定当时文件身份；只有用户明确批准该路径可被覆盖时才允许 replace，否则使用文件系统原子 create-only 发布，目标后来出现即失败并保留其内容。资源意图在创建任何文件前持久化；失败或删除失败保留 ledger 与对应额度并在线/后续启动重试。恢复仅清理宿主 ledger 已登记且所属 host 已确认退出的路径，不递归扫描猜测未知资源，也不删除其他活跃 host 的资源。

外部副作用不提供普遍事务回滚承诺。每个可写服务必须定义提交点与失败后状态；进程已退出但提交已完成时，宿主保留可查询的最终结果。首版不自动重放写操作。

提交目标令牌（`targetToken`）有两个来源：`files.pickWrite` 保存对话框选定的单文件，或 `files.createWriteTarget(directory?, suggestName)` 取得的自动命名目标。后者不弹对话框：`directory` 为空表示宿主管理的日志目录（打包等内置语义的默认输出位置），非空时必须解析为该插件经选择器授予并被宿主记忆的目录，解析失败返回 `PermissionDenied`。宿主负责清洗建议名中的非法字符、以两位序号后缀排解重名，并沿用上述 create-only 发布规则。`files.hostPaths` 向持有写权限的插件返回宿主日志目录等路径信息；该信息仅用于展示与提示，不构成任何文件访问授权。

## 14. 安装、更新与重启

安装/更新必须经过用户确认及基本包校验，不要求当前建立签名审批平台。新包写入独立版本目录，完成校验后标记待应用；不得覆盖正在执行的 DLL 或资源。新增权限必须重新确认。

插件管理器提供“应用并重启”，列出待更新插件并提示串口会话将关闭、发送任务会停止。用户可以取消，不自动重启。不支持插件间依赖图、热替换或更新后自动解除故障禁用。

应用流程：停止接受新工作 → 按宿主策略停止发送并关闭串口 → 刷新日志和保存设置 → 有限停用 worker → 持久化待切换版本 → 正常退出 → 下次启动在加载插件前完成切换和验证。

核心清理失败时必须报告并中止自动重启或交由用户明确处理，不能用插件退出期限强杀宿主。断电/切换失败要能恢复旧完整版本；配置迁移独立备份，不能仅回退 DLL 就宣称恢复成功。故障禁用状态跨更新保留。

## 15. 内置插件与分发

BuiltIn 仅是发布来源标记，不是另一套执行接口。背景图和日志打包 MUST 使用同一 manifest、runner、IPC、权限、资源预算、故障禁用及恢复流程。出厂清单可批准明确版本的初始权限，不意味着安装目录下任意新增 DLL 自动获信任。

背景图使用 `background-image`、`settings-panel`、`storage.own` 和 `files.user-selected.read`；由宿主渲染，不访问主窗口对象。日志打包使用 `menu`、可选的清单级 UI 能力组合、`serial.logs.read`、`storage.own`、`files.user-selected.write`，不访问 SessionViewModel；其输出目标由宿主解析与命名——默认跟随宿主日志目录，或为用户经目录选择授权的目录（§13），插件全程只持有不透明令牌。此处“可选组合”指开发者选择是否在清单声明，已声明能力仍为必需。

迁移必须保留背景图轮播设置、日志输出目录跟随行为及独立偏好文件中的既有数据。旧实现尚无公开执行 ABI，不凭空增加旧插件二进制兼容层。

安装版和 portable 版都必须携带 runner、受管依赖及内置包，不能假设只分发单 EXE 就自然包含外置插件。移除 BuiltIn 包后的验收是：背景图/打包正常缺席，串口收发、显示、日志与基础设置正常，而不是声称所有可选功能仍存在。

## 16. 开发者入门示例

下面是日志打包插件的清单设计示例；宿主版本 `0.1.0` 仅为占位，实际需使用首个实现 DPP/1 的宿主版本。运行时 API/schema 尚未发布，不能据此声称当前 DuCom 可加载该包。

```json
{
  "manifestVersion": 1,
  "id": "org.example.log-export",
  "name": "Log Export",
  "version": "1.0.0",
  "protocolVersion": "1.0",
  "minHostVersion": "0.1.0",
  "entryAssembly": "Example.LogExport.dll",
  "entryType": "Example.LogExport.Plugin",
  "runtime": { "framework": "net10.0", "rid": "win-x64" },
  "capabilities": ["menu"],
  "permissions": [
    "serial.logs.read", "storage.own", "files.user-selected.write"
  ],
  "defaultCulture": "en-US"
}
```

预期开发流程：选择已发布 SDK → 定义清单与最小权限 → 在 worker 中注册声明式菜单/页面 → 通过代理请求日志快照和输出令牌 → 实现取消与有界处理 → 本机显式安装启用 → 运行 §18 合规测试 → 提交包及源代码供维护者审核。

GitHub 分支、PR 和主分支合并规则由仓库治理文件定义，不嵌入线协议。维护者审核变更不等于其后每个本地安装包都经过认证；文档与 UI 必须保持这一差别。

## 17. 诊断与隐私

诊断包含插件 id/版本/摘要、激活代次、宿主版本、故障阶段、错误码、期限、资源采样与终止结果。每插件日志限速、限长度、合并重复消息，超限丢弃并计数，不阻塞核心。

默认不记录串口原始内容、文件正文、IPC 凭据、敏感配置或完整用户路径。用户导出诊断需可预览和脱敏。内存转储可能包含设备数据与凭据，不能在预警时未经说明自动收集上传。首版不要求遥测或联网报告。

## 18. 发布门禁与未冻结内容

| 测试 | 必须验证的结果 |
|---|---|
| 构造/初始化/运行期崩溃和 FailFast | 仅 worker 退出；核心继续；禁用持久化且一次提示。 |
| 死循环、阻塞、心跳正常但业务卡死 | 有界检测与终止，旧实例不复活。 |
| 多插件内存、CPU、进程和消息洪泛 | 工具总预算治理生效，按证据停用，不杀核心进程；验证私有提交量计量。 |
| 恶意文件/网络/设备/宿主进程访问 | OS 限制实际拒绝；不能仅检查 manifest 或日志。 |
| 畸形 UI、超大图片、复杂布局 | 验证有界渲染、受限解码和主窗口响应。 |
| 快慢消费者和持续丢块 | 核心接收/落盘不等待，gap 准确，持续拖慢者关闭。 |
| 日志追加、轮转、删除及取消 | 快照边界准确，失效明确，无假成功半成品。 |
| 重复错误、用户再试、更新后重启 | 每个失败代次恰好一次提示；只有用户操作可解除禁用。 |
| 旧 SDK 二进制、新旧版本矩阵 | 无需重编译旧插件，拒绝路径明确。 |
| 安装路径攻击、更新中断、配置迁移失败 | 不越界写入，可恢复完整包和原配置。 |
| 移除 BuiltIn、禁用全部插件启动 | 核心可用，安全启动覆盖内置插件。 |
| 安装版与 portable | runner 与包完整，重启切换行为一致。 |

压力测试必须给出无插件基线、串口配置/吞吐、持续时间、CPU、内存、丢失及日志完整性结果，不用“界面看起来正常”代替验证。危险插件在可终止测试环境运行。

正式 DPP/1.0 冻结前还必须交付：机器可校验的 manifest/IPC/UI JSON Schema、完整操作及 DTO 目录、版本化错误码、Windows 限制配置及兼容矩阵、内存/CPU 配额与默认期限实测、SDK API 和最小示例、旧二进制兼容测试、安装与恢复测试向量、中英文一致性检查。

以上是实现与发布门禁，不是尚待用户重新决定的产品方向。在完成前本文保持草案，不打兼容认证标签。
